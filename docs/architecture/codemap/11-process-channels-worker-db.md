# 11 process-channels-worker-db

## Purpose

Three main-process pillars. **Channels** (`src/process/channels/`) is the multi-platform remote-messaging framework: 25 built-in IM/email/webhook plugins convert platform-native messages into one unified protocol, gate them through pairing/authorization, and stream agent replies back (edit-driven or buffered). **Worker** (`src/process/worker/`) is the fork-process substrate: the `Pipe`/`ForkTask` IPC protocol plus the two forked entrypoints (`gemini.js` agent worker, `emailImap.js` IMAP/SMTP worker). **Database** (`src/process/services/database/`) is the single SQLite store (`wayland.db`): pluggable driver (better-sqlite3 / bun:sqlite), 50 versioned migrations (v50 = semantic-vector shadow tables), repository facades, and a streaming write buffer. Every assimilation feature that needs persistence, a remote surface, or an out-of-process runtime plugs into one of these three.

## Entry points & lifecycle — how and when this code runs

- **App boot**: `src/process/index.ts:43` calls `getChannelManager().initialize()` (after `ExtensionRegistry` init at :34). Failure is logged, never fatal to startup.
- **ChannelManager singleton** is anchored on `globalThis.__waylandChannelManager` (`src/process/channels/core/ChannelManager.ts:116-123`) because vite duplicates the module across chunks (statically imported by channelBridge, dynamically by conversationBridge) — a per-copy static would split live plugin state from the IPC that queries it.
- **Constructor** registers all 25 built-in plugin constructors via `registerPlugin(type, Ctor)` (`ChannelManager.ts:74-102`): telegram, lark, dingtalk, weixin, wecom, discord, slack, sms-twilio, whatsapp, email-agentmail, email-imap, matrix, line, webhook, irc, mattermost, google-chat, nextcloud-talk, synology-chat, nostr, twitch, bluebubbles, imessage, signal, ms-teams.
- **`initialize()`** (`ChannelManager.ts:129-190`): register extension-contributed channel plugins from ExtensionRegistry → construct `PairingService`, `SessionManager` (await `.ready` — sessions hydrate from DB), `PluginManager`, `ActionExecutor` → wire `PluginManager.setMessageHandler(actionExecutor.getMessageHandler())` and the tool-confirm handler (resolves user → session → `getChannelMessageService().confirm()`, :151-173) → `wireWebhookDispatcher()` (hydrate token store from `ProcessConfig.get('webhook.connectionTokens')` at :247, then `registerWebhookDispatcher` routes verified events to `plugin.handleWebhookPayload`, :256-272) → `loadEnabledPlugins()` reads `assistant_plugins` rows and starts each enabled one; plugin types not in `builtinStartableTypes` and not extension-provided are auto-disabled (:326-343).
- **`shutdown()`** (`ChannelManager.ts:196-224`): `pluginManager.stopAll()` → `pairingService.stop()` → `getChannelMessageService().shutdown()` → null out sub-components.
- **Webhook HTTP surface**: `src/process/webserver/index.ts:320-327` calls `mountWebhookRoutes(app, {getSecretForToken})` BEFORE the basic middleware so `/webhooks/*` gets its own `express.raw()` body parser and bypasses CSRF (authenticated by platform signatures instead).
- **Workers**: `src/process/task/BaseAgentManager.ts:41-49` extends `ForkTask` and forks `path.resolve(__dirname, type + '.js')` — so `src/process/worker/gemini.ts` is compiled to `out/main/gemini.js` and forked once per gemini conversation. `src/process/worker/emailImap.ts` → `out/main/emailImap.js` is forked by `EmailImapWorkerClient` (`src/process/channels/plugins/tier1/email-imap/EmailImapWorkerClient.ts:25`) so IMAP/SMTP sockets run off the Electron main loop. Fork mechanics: `ForkTask.init()` uses `platform.worker.fork` with cwd rewritten to `app.asar.unpacked` when packaged and env from `getEnhancedEnv()` (full shell PATH) (`fork/ForkTask.ts:50-63`).
- **Database**: `getDatabase()` is a lazy async singleton (`src/process/services/database/index.ts:1884-1892`) opening `<getDataPath()>/wayland.db` (:1880-1882). `DarhaiUIDatabase.create()` (:125-206) handles corruption recovery: only recovers on real corruption signals (`SQLITE_CORRUPT`, `SQLITE_NOTADB`, … :59-66), never on native-module load errors (:57, :153-159); backs up the bad file and deletes `-wal`/`-shm` sidecars (:172-199). `initialize()` runs `initSchema` + migrations up to `CURRENT_DB_VERSION = 50` (`schema.ts:191`) tracked via `PRAGMA user_version` (`schema.ts:170-185`). `closeDatabase()` is synchronous for `process.on('exit')` handlers (:1894-1906).

## Contracts & data flow

**IPC (main↔renderer)** — channels code emits on `channel` bridge from `@/common/adapter/ipcBridge` (handlers registered in `src/process/bridge/remote/channelBridge.ts`, outside this area): `pluginStatusChanged` (`gateway/PluginManager.ts:306,327`), `pairingRequested` (`pairing/PairingService.ts:87`), `userAuthorized` (`PairingService.ts:217,256`). Provider endpoints (get-plugin-status, enable/disable/test-plugin, pairing approve/reject, etc.) are listed in `channels/ARCHITECTURE.md` §8.

**Agent→Channel event bus** — single event name `channel.agent.message` on `channelEventBus` (`agent/ChannelEventBus.ts:13-16`). Agent managers emit per-conversation `IAgentMessageEvent` (an `IResponseMessage` + `conversation_id`); `ChannelMessageService` is the only consumer. This is the "dual-path broadcast": the same event also goes to the renderer via ipcBridge.

**Worker pipe protocol** — messages `{type, data, pipeId?}`; a `pipeId` requests a response on channel `<pipeId>.callback` with `{data, state: 'fulfilled'|'rejected'}` (`worker/fork/pipe.ts:53-58`, `ForkTask.ts:113-128`). Reserved types: `start`, `complete`, `error` (`WorkerProtocol.ts`). Gemini worker channels: `gemini.message` (stream events), `stop.stream`, `init.history`, `send.message`, plus per-tool-call `once(<callId>)` confirmations (`worker/gemini.ts:40-56`). Email worker channels: `email.connect/send/test/stop` + `email.message` (`worker/emailImap.ts:30-45`).

**Spawned processes & runtimes** — (1) fork workers `out/main/gemini.js` / `out/main/emailImap.js` via `platform.worker.fork` (Electron utilityProcess or node fork; env = `getEnhancedEnv()`, cwd = asar.unpacked when packaged, `ForkTask.ts:50-63`); (2) `whatsapp-bridge/bridge.js` node subprocess, JSON-RPC 2.0 over stdio, backend flag `--backend baileys|whatsapp-web|meta-business`; (3) signal-cli binary from `channels/signal-cli-runtime/`; (4) tunnel CLIs (cloudflared quick tunnel by default; binary lazily downloaded from cloudflare's GitHub releases, `tunnel/cloudflaredBinary.ts:40`).

**HTTP surface** — `POST|GET /webhooks/:platform/:connectionToken` on the shared webserver (`webserver/index.ts:320-327`); 1 MB payload cap; response codes: 404 unknown-token/platform/mismatch, 413 too large, 401/403 from verifier, 200 challenge/duplicate, 202 accepted, 503 no dispatcher (`webhook/WebhookReceiver.ts:145-250`).

**Config/storage keys (ProcessConfig)** — `webhook.connectionTokens` (persisted token records, secrets safeStorage-encrypted; hydrated at `ChannelManager.ts:247`); `assistant.<platform>.agent` (selected backend per channel, `ActionExecutor.ts:518`); `assistant.<platform>.defaultModel` with legacy fallback `assistant.telegram.defaultModel` (`actions/SystemActions.ts:87-89`); `model.config` (provider catalog, `SystemActions.ts:58`).

**DB file & tables** — file `<dataPath>/wayland.db` (`database/index.ts:1880-1882`), WAL mode, version via `PRAGMA user_version`. Base tables from `schema.ts`: `users`, `conversations` (+`source`, `channel_chat_id`), `messages`, `teams`, `mailbox`, `token_family`, `team_tasks`, `team_event_log`. Migration-added (with version): `assistant_plugins`/`assistant_users`/`assistant_sessions`/`assistant_pairing_codes` (v7), `cron_jobs` (v9, desc v24), `remote_agents` (v16-18), `acp_session` (v26), `token_blacklist` (v29), `webui_paired_devices` (v34), `model_registry` (v39), `usage_events` (v40), `workflow_sessions` (v41-42), `projects` (v43), lease columns on `team_tasks` (v45), `teams.verification_policy` (v46), `channel_welcome` (v47), `cost_events` (v48), `budgets` (v49), `vec_skills_meta`/`vec_memory_meta` (v50). v50 tables are fingerprint shadow tables only — the actual `vec0` virtual tables are created at runtime by `src/process/services/semantic/SqliteVecStore.ts` after `driver.loadExtension()` loads sqlite-vec; if unavailable, retrieval falls back to keyword search (`migrations.ts:2187-2195`).

**Conversation scoping** — a channel conversation is keyed `(user_id, source=platform, channel_chat_id, type[, extra.backend])` via `findChannelConversation` (`database/index.ts:597-643`); name format `{tg|ding|wx|wecom|<platform>}-{type}[-{backend}]-{chatId[:8]}` (`channels/types.ts:796-813`). Sessions are keyed `userId:chatId` in `SessionManager`.

**Credentials at rest** — `assistant_plugins.config` column stores `{credentials, config}` JSON; sensitive string fields encrypted `enc:v1:` via safeStorage on write (`database/index.ts:1318-1324`), decrypted on read (:1230, :1277); classification lives in `@process/secrets/fieldClassification`. `remote_agents` encrypts auth_token/device keys the same way (:1798-1805, :1836).

**File formats** — webhook audit JSONL `<userData>/webhook-audit.log` (10 MB rotate, `.1` keeps one generation); agent-output media protocol `[DARHAI_CHANNEL_SEND]{"type":"image|file","path":...}[/DARHAI_CHANNEL_SEND]` parsed by `utils/channelSendProtocol.ts:12`.

## Conventions & invariants

- **Every DB method returns `IQueryResult<T>`/`IPaginatedResult<T>`** — never throws to callers; repositories (`Sqlite*Repository`) are the async facade that unwraps and throws. New tables get: schema in a numbered migration (with `down`), `CURRENT_DB_VERSION` bump in `schema.ts:191`, and a `migration_vNN.bun.test.ts`.
- **Migrations are additive and transactional** — all pending migrations run in one transaction with FK off and a `foreign_key_check` afterwards (`migrations.ts:2274-2300`). Never edit an existing migration; append a new version.
- **Snake_case rows ↔ camelCase models** with explicit converter pairs (`types.ts`, `channels/types.ts:623-710`). JSON-blob columns (`extra`, `config`, `model`) are queried with `json_extract`.
- **Plugins are registered in three synchronized places** — `registerPlugin()` in the ChannelManager constructor, `builtinStartableTypes` in `loadEnabledPlugins` (`ChannelManager.ts:288-323`, comment warns stale lists silently auto-disable user plugins), and `getPluginTypeFromId` prefix mapping (:791-829, longest-prefix-first). A channel that should auto-approve tools must ALSO be added to `CHANNEL_AUTO_APPROVE_SOURCES` (`channels/types.ts:748-763`) or tool turns hang on unconfirmable prompts.
- **Capability flags drive behavior, not platform switches** — `canStream && canEdit` → edit-driven streaming, else buffered (`ActionExecutor.ts:719-725`); optional behaviors (typing indicator, flushTextDraft) are duck-typed, never added to BasePlugin mid-flight.
- **Webhook trust model** — connection token (unguessable URL) + per-platform signature verifier + replay cache; tunnels change reachability only, never trust (`tunnel/types.ts` header). Verifiers are pure (verify + parse, no dispatch). Receiver always answers the platform with a stable status; plugin handler errors never leak.
- **Secrets**: any new credential-ish string field must be classified in `@process/secrets/fieldClassification`; plaintext persistence must fail loudly (`webhook/connection-tokens.ts:22-33`).
- **Singletons** use `getX()` accessors; ChannelManager specifically must stay globalThis-anchored (vite chunk duplication, `ChannelManager.ts:108-123`).
- **One turn at a time per conversation** — `ChannelMessageService.sendQueues` serializes sends with a bounded 20 s gate; never dispatch a second turn into an active stream.
- **Worker processes own their sockets** — anything with long-lived I/O (IMAP IDLE) goes into a fork, main process talks over the pipe protocol only; no Electron APIs in `src/process/worker/` (AGENTS.md process-type rule).

## Assimilation anchors

- **New messaging channel** → directory `src/process/channels/plugins/tierN/<name>/` with `<Name>Plugin.ts` (extends `BasePlugin`, declares `capabilities`) + `<Name>Adapter.ts` (pure conversion). Imitate `plugins/tier2/matrix/MatrixPlugin.ts` (socket-based) or `plugins/tier2/line/LinePlugin.ts` (webhook-based). Register in the 3 ChannelManager spots + `testPlugin` branch (:709-717 pattern) + credential fields in `channels/types.ts:67-146` + `hasPluginCredentials`; webhook channels also add a verifier in `webhook/verifiers/` and its `VERIFIER_REGISTRY` entry.
- **New DB table / schema change (e.g. ECC instincts, IJFW memory index)** → append `migration_v51` in `services/database/migrations.ts` mirroring `migration_v50` (:2197-2216: `CREATE TABLE IF NOT EXISTS` up, `DROP TABLE` down, added to `ALL_MIGRATIONS` :2222), bump `schema.ts:191`, add `migration_v51.bun.test.ts` copied from `migration_v50.bun.test.ts`. Access via a new `I<X>Repository` + `Sqlite<X>Repository` pair mirroring `SqliteAcpSessionRepository.ts` (prepared statements over `getDatabase().getDriver()`).
- **Vector/semantic data for new content types** → follow the v50 pattern: plain fingerprint shadow table in a migration + runtime `vec0` virtual table in `src/process/services/semantic/SqliteVecStore.ts` (uses the optional `driver.loadExtension` seam, `drivers/ISqliteDriver.ts:21`).
- **New out-of-process runtime (e.g. a local model host, ECC daemon)** → either (a) a fork worker: entry file in `src/process/worker/<name>.ts` using `pipe.on(...)` like `worker/emailImap.ts`, driven by a main-process `ForkTask` subclass like `EmailImapWorkerClient.ts`; or (b) a stdio-JSON-RPC subprocess like `channels/whatsapp-bridge/bridge.js` with an explicit method allowlist (`allowlist.js`).
- **New channel command/action** (e.g. `/workflow run`) → handler + entry in `actions/SystemActions.ts:841-896` (or a new `<X>Actions.ts` array registered in `ActionExecutor.registerActions()` :1082-1097); action names are `category.verb` strings routed by `actionRegistry`.
- **Exposing a local service publicly** → reuse `tunnel/WebhookExposureService.resolveExposure` (user URL > opt-in tunnel > none) rather than spawning your own tunnel; add the platform to `webhookExposureGuard.PUBLIC_WEBHOOK_PLATFORMS` only if the provider must call back over the public internet.
- **Agent reply → channel delivery for a new agent type** → nothing channel-side to change if the agent manager emits `channelEventBus.emitAgentMessage(conversationId, event)` and registers under a `conversation.type` handled by `resolveChannelConvType` (`channels/types.ts:777-786`) + `rowToConversation` (`database/types.ts:136-215`) — those two switches, plus the `{input}` vs `{content}` payload branch in `ChannelMessageService.ts:312-317`, are the only type-sensitive seams.
