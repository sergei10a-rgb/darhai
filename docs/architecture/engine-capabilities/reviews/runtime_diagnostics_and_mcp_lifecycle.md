# Review: runtime_diagnostics_and_mcp_lifecycle

Verdict: **needs-work** - 6 findings

## [HIGH] The mutation proof leaves TEN guards unprotected: I mutated 15 guards the author did not, and 10 survived with the suite still 90/90 green. Survivors: booleanFault (deferred/resources_declared/resources_exposed/assistant_scoped), tool_count integer+range, optionalStringFault (display_path/executable_basename/profile_name), the unknown-key check on `process`, the unknown-key check on `unsupported_overrides`, the `failure` enum check, MAX_CONFIG_SOURCES, MAX_UNSUPPORTED_OVERRIDES, the unavailable `diagnostics_version` 0..65535 range, and the unknown-key check on `config_source`. I probed all ten behaviourally: each guard actually works today, so this is a test-suite defect, not an implementation one — but nothing stops a future refactor from deleting any of them silently. The AUTHOR CLAIM 'mutation proof: 38 mutations ... all caught' is materially overstated for a criticality:safety decoder.

**Where:** tests/unit/wcore-runtimeDiagnostics.test.ts (no case exercises any of these) against src/process/agent/wcore/capabilities/runtimeDiagnostics.ts:529 booleanFault, :536 integerFault via :1041 tool_count, :545 optionalStringFault, :1131 decodeProcessBinding unknown-key, :988 decodeUnsupportedOverride unknown-key, :1082 failure enum, :188 MAX_CONFIG_SOURCES, :189 MAX_UNSUPPORTED_OVERRIDES, :1255 unavailable version range, :950 decodeConfigSource unknown-key

**Why it matters:** Reproduced with a scripted harness (backup -> patch one guard -> `node ./node_modules/vitest/vitest.mjs run tests/unit/wcore-runtimeDiagnostics.test.ts --reporter=json` -> restore, md5 verified identical after). Example: replace booleanFault's body with `return undefined;` -> 90/90 still pass, yet an engine sending `"deferred": "false"` now decodes to a TRUTHY `deferred` in the frame (the module's own comment at :530 says `"false"` being truthy is why the guard exists), and the UI reports a server as deferred when the engine said it is connected. Same for `tool_count: -1` and for a 65th config_source silently accepted.

## [HIGH] Every cap bounds the NUMBER of entries; none bounds their SIZE. `mcp_servers[].name` has no maxLength in the schema, and enumFault embeds `JSON.stringify(value)` of an arbitrary engine string into each unreadable reason — so one event can force a multi-tens-of-MB frame across the renderer IPC boundary and the same volume into the on-disk log. This directly contradicts the file header's claim that the caps 'bound the LOOP and the emitted frame'.

**Where:** src/process/agent/wcore/capabilities/runtimeDiagnostics.ts:167-190 (cap rationale), :525 enumFault JSON.stringify, :1091 salvageName, :1120 unreadable.push, :1506-1509 the warn detail; consumed at src/process/task/WCoreManager.ts:1081 (IPC emit) and src/process/utils/configureConsoleLog.ts (console.warn -> 10 MB rotating file)

**Why it matters:** MEASURED with tsx against the real module. Case A, a FULLY SCHEMA-VALID snapshot of 256 mcp_servers each with a 100k-char `name`: emitted frame = 25.7 MB, decode 1 ms. Case B, 576 rows (256 servers + 64 config_sources + 256 overrides) each carrying a 100k-char unknown enum value: frame = 57.7 MB AND ctx.warn detail = 57.6 MB, decode 181 ms. The 57.7 MB frame is structured-cloned to the renderer; the 57.6 MB warn is written to a log file capped at 10 MB, so a single hostile or buggy snapshot rolls the log and destroys the forensic history the capability exists to provide.

## [MEDIUM] The redaction invariant is incomplete: the module keeps the three declared free-form fields (display_path, profile_name, executable_basename) out of the log, but enumFault echoes ANY unknown enum value verbatim, and handleSnapshot logs every unreadable reason. An engine value that happens to be a path therefore reaches disk. The redaction test cannot catch this because it only checks the three known field values against the happy fixture.

**Where:** src/process/agent/wcore/capabilities/runtimeDiagnostics.ts:523-527 enumFault, :1503-1510 the warn that ships the reasons, documented invariant at :1403-1414; test tests/unit/wcore-runtimeDiagnostics.test.ts:1177-1204

**Why it matters:** MEASURED: a snapshot whose single server carries `working_directory: "/home/serge/secret-project"` produces the log line `runtime_diagnostics_snapshot "runtime-diagnostics-001" carried 1 entr(ies) this build cannot read ["mcp_servers[0]: working_directory has unknown value \"/home/serge/secret-project\""]`. console.warn is routed to a dated file by configureConsoleLog.ts, which is exactly the bug-report artefact the header says must never carry a home directory. `working_directory` is the likeliest field to widen this way — its own enum contains `explicit`, i.e. 'a path was configured'.

## [MEDIUM] The capability does nothing in the shipped app: it is not registered, its reply types are still declared knowingly-ignored, and neither send function has a caller. `resetRuntimeRequests` — the documented seam for a restarted engine — is likewise never called outside the test.

**Where:** src/process/agent/wcore/capabilities/index.ts (HANDLERS = executionPolicy, workflowLifecycle, anvilReceipts, budgetGrants — runtimeDiagnosticsCapability absent); src/process/agent/wcore/protocol.ts:373,376,377 (all three types still in ACKNOWLEDGED_UNHANDLED_EVENTS)

**Why it matters:** Verified by grep: the only references to sendGetRuntimeDiagnostics / sendRemoveMcpServer / runtimeDiagnosticsCapability / resetRuntimeRequests outside the module are in tests/unit/wcore-runtimeDiagnostics.test.ts. So today a real runtime_diagnostics_snapshot is swallowed by the acknowledged-inert check and no button can send either verb. The header discloses this as three pending edits, which is honest — but it means every claim in this review is module-local and none of it is exercised on the wire.

## [LOW] `requestedVersion` presents an engine echo as the version the HOST asked for, and the log says so in words. The host can only ever send `diagnostics_version: 1` (schema `const: 1`), so any other echoed value is an engine fault, yet the module renders it as the user's own request. The removal path cross-checks the echoed `name` against the ledger for exactly this reason; the version gets no equivalent check because the pending entry does not record it.

**Where:** src/process/agent/wcore/capabilities/runtimeDiagnostics.ts:480-481 (field doc), :1276, :1537-1539 (the log line); pinned by tests/unit/wcore-runtimeDiagnostics.test.ts:953-966

**Why it matters:** Measured: feeding a runtime_diagnostics_unavailable with `diagnostics_version: 65535` yields a frame `requestedVersion: 65535` and the log line `diagnostics <id> unavailable (invalid_request); asked for 65535, engine serves 1`. Darhai never asked for 65535 and cannot. For a safety-graded capability whose purpose is to stop the host guessing, this is a confident wrong statement written to disk.

## [LOW] The host-only REQUEST_ID_PATTERN is enforced against INBOUND request_ids, where neither schema imposes any pattern (only minLength/maxLength, plus x-maxUtf8Bytes:256 on the lifecycle verb, which the code never checks). A schema-conformant reply whose id falls outside the host's character class is classified as having no readable request_id and settles nothing at all.

**Where:** src/process/agent/wcore/capabilities/runtimeDiagnostics.ts:213-224 REQUEST_ID_PATTERN, :607-613 requestIdFault, applied inbound at :1171, :1248, :1299; contract: core-event.schema.json request_id = {minLength:1,maxLength:128|256} with no `pattern`

**Why it matters:** Measured: `request_id: "mcp rm 001"` is rejected with `request_id must match ^[A-Za-z0-9][A-Za-z0-9._:-]{0,255}$`. Harmless while the host mints every id, but the module's whole design assumes the engine may echo ids it did not have to normalise. If any engine build ever prefixes or reformats the correlation key (a `session/` prefix, a UUID with braces), settleUndecodable takes the requestId===null branch, emits nothing, and the caller spins forever — which is the precise failure mode this capability was written to remove.
